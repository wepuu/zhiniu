# Phase 21 — Invite Beta 运营闭环

## 状态

Phase 21 的代码与数据库结构已实现，但外部邀请仍为 **blocked**。系统按 fail-closed
处理：只有最新 Phase 20 验收通过且 Beta eligible、法律与数据使用状态获批、注册模式为
`invite_only`、真实 Resend 发布配置及 active 诊断健康、容量未满时，批次才可批准和投递。

当前基线仍包含 Phase 20 数据完整性、开发评估数据使用范围以及真实邮件配置门禁，运营人员
可以创建草稿和预检，但不得用模拟结果绕过批准。

## 运营流程

1. 运营人员进入 `/admin` 的“邀请内测”，创建有目标人数和到期时间的草稿批次。
2. 添加明确同意参与测试的邮箱。邮箱会规范化，并用 HMAC 用于跨批次去重。
3. 检查页面列出的门禁原因。批准和投递均重新读取最新门禁，避免批准后环境漂移。
4. 通过 step-up 验证的运营人员批准批次，再执行投递。每个邮箱产生一个一次性、到期、
   邮箱绑定的注册码和一个可查询的邮件投递记录。
5. 邮件链接预填并锁定受邀邮箱。注册时服务端再次校验批次状态、受邀状态和邮箱 HMAC；
   注册成功后原子消费邀请码并关联用户。
6. 运营台从真实交付、验证、自选和反馈记录计算漏斗。关闭批次会撤销尚未消费的邀请码。

## 安全与隐私

- 邀请写操作需要 cookie 会话、CSRF、允许的 Origin、运营能力和短时 step-up。
- 邀请码只在创建邮件任务时短暂存在；数据库只保存摘要，日志和审计不保存明文邀请码、
  邮件正文、密钥或 cookie。
- 用户的自选和反馈继续按 `user_id` 隔离。
- 运营台移动端只读查看；批准、投递和关闭按钮只在桌面布局显示。

## 验收清单

- 迁移头为 `20260825_0026`，`alembic check` 无漂移。
- 草稿支持邮箱规范化、批内/跨批去重、目标人数限制和已注册用户拒绝。
- 门禁不满足时批准与投递均失败且不创建邮件投递。
- 邮箱不一致、批次非 active、邀请码已使用/过期/撤销时注册失败。
- 用户引导状态来自既有持久化事实，不由前端猜测。

## 已知限制与后续门禁

Phase 21 不开放公开注册、不扩充数据覆盖、不开展营销邮件、不引入行为追踪，也不宣称生产
就绪。外部投递前仍需生成通过且 Beta eligible 的 Phase 20 验收记录，发布真实 Resend
配置并获得健康诊断；首批应小规模、可暂停，并每日查看退信、投诉和产品反馈。
